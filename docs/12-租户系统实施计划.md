# 租户系统实施计划

版本：v1.0  
日期：2026-09-07  
依据：`10-租户系统需求.md`、`11-租户系统技术.md`

前端：`grow_admin`  
后端：`grow_admin_server`

## 1. 怎么切阶段

按**可演示、可验收的垂直切片**推进：同一阶段同时改后端和必要的前端，而不是先做完全部后端再开前端。

每个阶段结束时必须能回答：

1. 用户能看到/测到什么？
2. 用哪几条需求验收项证明做完了？
3. 下一阶段依赖什么？

产品规则以需求文档为准。接口路径、表结构、JWT 字段以技术文档为准，本计划不重复抄表。

## 2. 现状（计划起点）

| 层 | 已有 | 缺口 |
|---|---|---|
| 数据库 | `sys_tenant`（状态 0/1，编码全表唯一）、`sys_account`（已有 `tenant_id`、`is_platform_admin`） | 生命周期字段、授权表、别名、审计、角色表 |
| 后端 | 登录 + 验证码 + JWT（claims 含 `tenantId/tenantCode/platformAdmin`） | 不校验租户状态；无 `TenantContext`；无 `/platform/**`；`base-org` / `base-access` 等模块为空 |
| 前端 | 系统管理页面已齐（mock）；登录只有账号密码 | 不传 `tenantCode`、无验证码；请求 `/login` 与后端 `/account/login` 不一致；无平台管理、无代操作横幅 |

**专项范围：** 租户隔离基础设施、登录/代操作、平台管理三页、生命周期、授权上限、账号/角色/菜单租户规则、清空、到期、`platform` 迁移。

**不纳入本专项：** 部门/岗位/人员完整后端实现、套餐计费、品牌、独立平台后台。那些模块后续落地时必须从第一天带 `tenant_id` 并走 `effectiveTenantId`。

## 3. 阶段总览

```text
阶段 1 调研计划        ✅ 本会话完成
    ↓
阶段 2 库表与种子       可独立执行
    ↓
阶段 3 登录与上下文     第一个可联调切片（含代操作 JWT）
    ↓
阶段 4 租户生命周期     平台超管可开户/试用/开通/停用/删除
    ↓
阶段 5 授权上限         依赖最小菜单表；TENANT_ADMIN 开始有意义
    ↓
阶段 6 租户账号         标准开户链路闭环：授权 → 建账号 → 分配管理员 → 开通 → 登录
    ↓
阶段 7 菜单/角色租户化  租户侧系统管理按规则改造
    ↓
阶段 8 代操作体验+审计  横幅、禁平台管理、审计页
    ↓
阶段 9 清空/到期/隔离   高危操作与收口
    ↓
阶段 10 联调验收        需求第 7 节 20 条
```

建议不要并行跳阶段：3 依赖 2，4 依赖 3 的上下文与会话作废，5 依赖 4 的租户实体，6–8 依赖 5 的授权数据。

## 4. 分阶段说明

### 阶段 1：调研与计划

**产出：** 本文档与规划文件。

**验收：** 阶段边界、依赖、不做清单已写清。

---

### 阶段 2：数据库升级与 platform 种子

**后端**

- 按技术文档升级 `sys_tenant`：生命周期状态改为字符串枚举；去掉全表 `uk_sys_tenant_code`；增加 `active_code` 生成列保证试用中/已开通编码唯一。
- 新建：`sys_tenant_menu`、`sys_tenant_menu_function`、`sys_tenant_menu_alias`、编码变更日志、代操作审计。
- 新建最小 `sys_role`（至少支持 `tenant_id + role_code` 唯一、`TENANT_ADMIN` / `built_in`）。完整角色 CRUD 可留到角色模块，但创建租户必须能插入这一行。
- 迁移：`platform` 设为内置、`status=active`、无到期约束；`admin` 保持 `is_platform_admin=1`。
- 现网无 Flyway：同时提供「全新初始化」脚本和「已有库增量」脚本。

**前端：** 无。

**验收**

- 新库、旧库都能升到新结构。
- `platform` 只有一行，且为内置已开通。
- 编码在 `trial/active` 下唯一，过期/停用/删除后可被新租户占用（库层约束成立即可）。

---

### 阶段 3：租户上下文与登录闭环

这是第一条业务切片。做完后，即使还没有租户管理页，也可以用 SQL 造一个 `trial` 租户验证登录。

**后端**

- 请求上下文解析 JWT，得到 `effectiveTenantId = impersonating ? actingTenantId : tenantId`。
- 登录流程按技术文档 4.4：先解析可登录租户（优先 `trial/active`），再校验状态与 `now <= expired_at`（上海时区）；过期则拒绝并回写 `expired`。
- 代操作：目标租户无同名账号时，用 `platform` 超管密码进入；JWT 增加 `impersonating`、`effectiveTenant*`、`operator*`。
- 会话作废：Redis 增加「租户 → sessionId」索引。停用/到期/删除删该租户全部 refresh token；改编码不删。
- 非代操作才更新账号和租户的 `last_login_at`。

**前端**

- 登录表单增加组织代码，默认 `platform`。
- 对接验证码与 `POST /account/login`。
- token / 用户状态补齐 `platformAdmin`、`impersonating` 等字段（横幅可下一阶段再画）。

**验收（对应需求 5、7、10、16 的登录部分）**

- `platform / admin` 可登录。
- 未开通、已停用、已删除、已到期分别提示具体原因。
- `now > expired_at` 即使状态仍是 `active` 也按已到期拒绝。
- 目标租户无同名账号 → 代操作 token；有同名账号 → 普通登录。
- 代操作不更新目标租户最后登录时间。

---

### 阶段 4：租户生命周期（平台管理 / 租户管理）

**后端：** 技术文档 4.1 全部接口。创建成功状态为 `not_opened` 并插入 `TENANT_ADMIN`。不提供通用改状态接口。`platform` 拒绝试用/开通/停用/删除/改编码/清空/授权。

**前端**

- 新增「平台管理」一级分组与租户管理列表。
- 筛选、列、操作按需求 5.2–5.6。
- 试用/开通弹窗只选结束日；改编码、删除二次确认。
- 本阶段路由可先用超管标记硬编码展示；阶段 7/8 再接到动态菜单与代操作隐藏。

**验收（需求 1–4、6、19 的主体）**

- 非超管不可见平台管理（后端 `/platform/**` 必须拒绝，不能只靠前端藏菜单）。
- 新建租户 = 未开通 + 有 `TENANT_ADMIN` + 无账号无部门无菜单。
- 创建/编辑表单不出现服务期限和状态下来选。
- 停用、删除立即作废该租户登录态。

---

### 阶段 5：授权上限与 TENANT_ADMIN 同步

**前置：** 授权树需要菜单 ID。若菜单模块尚未建表，本阶段先建最小 `sys_menu` / `sys_menu_function`，并种子化系统管理 + 平台管理菜单。完整菜单管理 CRUD 不是本阶段目标。

**后端：** `grant/detail`、`grant` 覆盖写；同步 `TENANT_ADMIN`；清理普通角色越权；新平台菜单只写入 `platform` 授权表；授权树不含平台管理节点。

**前端：** 租户列表「授权」页（菜单树 + 功能 + 最近授权人/时间）。

**验收（需求 9、12、15）**

- 保存后 `TENANT_ADMIN` = 当前上限全集。
- 取消某菜单后，普通角色对应授权被清掉；已登录用户下次请求失败，不立即踢下线。
- 给 `platform` 新增菜单不走授权 UI，自动拥有。

---

### 阶段 6：租户账号

**后端：** `/platform/tenant-accounts/**`；系统管理账号接口强制 `effectiveTenantId`。仅此入口可分配 `TENANT_ADMIN`。不可给非 `platform` 账号打超管标记。

**前端**

- 平台管理 / 租户账号：按租户筛选、创建、分配租户管理员。
- 系统管理 / 账号管理：当前租户；仅 `platform` 显示「平台超级管理员」开关。

**验收（需求 8、10、11）**

- 标准开户顺序可走通：创建租户 → 授权 → 建账号并分配管理员 → 试用或开通 → 用该租户编码登录。
- 开通前创建的账号不能登录。
- 租户侧列表看不到平台超管。

---

### 阶段 7：菜单与角色租户化

**后端**

- 侧边栏菜单 = 已授权平台菜单（套 alias）∪ 本租户自建，按 `parent_id` 合成一棵树。
- 租户改平台菜单只写 alias；自建仅 `automation` / `external`。
- 保存普通角色权限时做子集校验；保存 `TENANT_ADMIN` 权限的接口直接拒绝。

**前端**

- 菜单管理按「平台下发 vs 自建」切换可编辑字段和按钮。
- 角色管理：`TENANT_ADMIN` 行保护，权限抽屉只读并提示「与租户授权同步」；普通角色树过滤。

**验收（需求 12–14）**

- 租户不能删/停用/改路径平台菜单，只能改本租户显示名。
- 自建可改挂载位置，与系统菜单同树。
- 无菜单管理功能权限时不能增改删自建菜单。

---

### 阶段 8：代操作体验与审计

**后端：** `impersonating=true` 时拒绝全部 `/platform/**`；WebFilter 对代操作请求写审计（含 GET，参数脱敏）。

**前端：** 顶部横幅（租户名、编码、平台账号）+「退出登录」；代操作时不渲染平台管理，直链访问也进不了。

**验收（需求 16、17）**

- 不从租户列表进入代操作。
- 代操作接口调用都有审计；失败也记。
- 退出代操作必须重新用 `platform` 登录。

---

### 阶段 9：清空、到期任务与隔离收口

**后端**

- `clear-impact` / `clear-data`：二次确认（编码 + 原因）；按注册表物理删除已存在的业务表；保留租户、授权两表、alias（本期保留）、`TENANT_ADMIN`、两类日志；再按授权重建 `TENANT_ADMIN` 权限。
- 到期任务：扫描 `trial/active` 且 `expired_at < now`（排除 `platform`），改为 `expired` 并作废会话。登录补偿仍保留。
- 给空模块写隔离约定：Mapper 必须带 `effectiveTenantId`；禁止信任前端 `tenantId`。

**前端：** 清空前展示影响数量；二次确认。

**验收（需求 6、18）**

- `platform` 不能清空。
- 已删除租户允许清空。
- 清空后菜单上限仍在，账号/组织/普通角色/自建菜单没了。
- 23:59:59 上海时区到期后不可登录。

清空注册表第一期只登记**当时真实存在**的表。组织/设计器/运行时表出现后追加，不要提前删不存在的表。

---

### 阶段 10：联调验收

按需求文档第 7 节 20 条逐条过，并补：

- 编码复用后旧租户再开通应提示撞码。
- 改编码后旧 token 可用至过期，新编码才能新登录。
- 用租户 A 的 token 请求租户 B 数据必须失败。
- 未授权任何菜单的账号，租户可登录后能进空首页。

## 6. 风险（实施时优先防）

1. 漏加 `tenant_id` 或信任前端传入的 `tenantId` → 串租户。阶段 3 就把上下文做成强制过滤。
2. 没有租户级 session 索引 → 停用/删除无法立即下线。阶段 3 必须做。
3. 授权只做前端勾选、后端不校验子集 → 越权。阶段 5/7 后端强校验。
4. 清空误删 `platform` 或授权表 → 阶段 9 先跑影响范围接口，代码写死保护名单。
5. 到期只改列表状态、登录不看 `expired_at` → 阶段 3 登录以时间为准。

## 7. 建议的执行方式

1. 一次只进入一个阶段，阶段验收通过再开下一阶段。
2. 每阶段先补后端测试（登录、生命周期、授权），再改前端页面。
3. 前端平台管理页面落在独立模块 `cornerstone-apps-tenant`。
4. 阶段 4 起所有 `/platform/**` 在后端校验 `platformAdmin && !impersonating`，不要等阶段 8 才加。
