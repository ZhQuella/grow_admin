# 菜单目录与组装（设计备忘）

版本：v0.1  
日期：2026-09-08  
状态：方向备忘，尚未纳入当期实施

本文记录「能力目录」与「导航组装」拆分的讨论结论。现行菜单交互仍以 `06-菜单管理.md` 为准；租户下发与自建规则仍以 `10-租户系统需求.md` 为准。未改需求、未排期前，不在租户管理中新增平行的菜单管理页。

## 1. 背景

当前菜单同时承担两件事：

- **能力登记**：页面编码、路由、组件、功能权限、表定义。
- **导航分类**：目录、上级、排序、侧栏结构。

平台「系统管理 / 菜单管理」维护的是同一棵树。租户授权只决定「给不给」，不决定「挂在哪」。因此租户侧栏会继承平台分类（例如一直挂在「系统管理」下）。

开源 admin 的使用方装了 `apps-system` 等模块后，通常也不想原样接受模块自带的一级目录，更希望把账号、人员、部门放到自己的「组织」下。

## 2. 建议拆分

| 层 | 职责 | 不管什么 |
|---|---|---|
| 能力目录 | 扁平登记可安装的页面：编码、路由、组件、功能点、来源（内部应用 / 自动化 / 外链） | 目录层级、侧栏分类 |
| 菜单组装 | 编排导航：目录、挂载、排序、多套默认结构（模板） | 发明新的内部应用路由 |
| 租户授权 | 从已组装（或可组装）的能力中勾选上限 | 改路径、改组件、自建内部应用页 |

「只新增、不管层级」指的是能力目录。树、目录、默认结构交给组装。

租户可以不依赖模块自带的**分类树**，仍必须依赖已安装模块的**页面目录**。内部应用页由代码模块贡献，组装只是挑选和分组，不能由租户发明新组件。

## 3. 正确分层（开源框架）

不要把入口放在「租户管理里再开菜单管理 + 菜单组装」。正确位置是框架原语，租户只是其中一个消费者：

1. **能力目录**：各 Cornerstone 模块扁平贡献（编码、路由、组件、功能点）。
2. **菜单组装**：宿主或平台超级管理员编排默认导航；可多套模板（例如企业默认 / 学校默认 / 精简）。
3. **租户授权**：只勾这套树里的菜单和功能上限。

单租户使用方同样需要「自己排菜单」。现有「租户菜单」页适合继续展示某租户**生效结果**，而不是再维护一份菜单定义。

和现有代码的关系：各包的 `route-config` / 页面编码已接近能力目录；缺口是模块还同时贡献一级目录（如 `SystemCatalog`、`TenantCatalog`），`sample/mock/buildMenuList.ts` 只是把这些树拼在一起。组装应改由宿主拥有导航树，而不是拼接模块自带分类。

## 4. 评估结论

### 4.1 作为当前租户产品

完整方案（租户管理下独立「菜单管理」只新增 + 另页「菜单组装」给每个租户一套不依赖系统菜单的结构）**现在不值得做**。

- 真正痛点是导航信息架构，不是缺一套租户菜单表。
- 与现行规则冲突：平台统一下发、租户只能改显示名、自建仅自动化和外链且不能建目录。
- 授权树、`TENANT_ADMIN` 同步、别名、自建挂载、角色权限树都要改模型，成本和「分类更灵活」不成比例。
- 与「系统管理 / 菜单管理」重名，职责不清。

若只是「系统管理」这个分组难看：优先租户显示名，或授权时允许改挂载目录。

### 4.2 作为开源 admin 框架

**值得做成框架能力**，作为中期方向，而不是本期租户页面。

- 模块化后台的核心诉求是：安装模块后，由宿主决定导航，而不是接受模块自带分类。
- 这接近 contribution point：模块贡献页面，宿主组装侧栏。比「一张菜单表既是目录又是树」更适合开源框架。
- 默认仍要提供一套开箱即用的组装结果（当前 sample 侧栏可作为第一套模板），避免拆分后 clone 即跑失败。

## 5. 明确不做（本期）

- 不在租户管理下新增第二套「菜单管理」。
- 不让每个租户各自维护一份内部应用菜单定义（升级时无法对齐模块发版）。
- 不通过自建菜单突破平台功能上限。
- 不把「组装」理解成租户可以注册新的内部路由 / 组件。

## 6. 建议演进（未排期）

1. 模块改为扁平贡献能力，不再强制带一级目录。
2. sample 保留一棵默认组装树，作为第一套模板。
3. 租户授权改为「套模板 + 再裁剪」。
4. 现有只读「租户菜单」展示该租户实际生效的组装结果。
5. 再考虑多模板、按租户覆盖目录。出现明确垂直差异（如教育 / 政务必须用完全不同的一级目录）时，再上多套组装模板。
